01 · 核心概念

AI Agent 是什麼？

能把任務往前推進多步，使用工具或環境回饋，再決定下一步的系統。

模型

理解任務並選擇下一步。

工具

搜尋、計算或連接外部系統。

控制

保存必要狀態、檢查結果並停止。

具體 Agent 產品的定義和 runtime 會不同；這裡先用共同概念建立直覺。

02 · 和聊天機器人的差異

回覆一次 vs. 推進任務

一般問答

問題 → 文字答案

通常不會真的操作外部工具。

Agent 任務

目標 → 選工具 → 取得結果 → 再決策

工具結果會影響後續行動。

使用者給目標→Agent 推進→完成或回報

是否稱為 Agent 取決於產品/研究定義；重點是有沒有多步行動與動態決策。

03 · 工具使用

Agent 怎麼使用工具？

1

模型選擇適用工具，提出結構化參數。

2

執行環境驗證並呼叫工具。

3

工具回傳結果，模型讀取後續做或停止。

模型提出「要查什麼」；連接的工具才真的去查。若工具沒有修改權限，就不能聲稱已完成修改。

Toolformer 研究如何讓模型學會何時呼叫 API；這和每個 Agent runtime 的實際工具介面不同。

04 · 行動循環

看懂 ReAct：行動後要看結果

任務→行動→觀察→更新下一步↺

ReAct 論文探討模型把推理軌跡與任務行動交錯，使模型能從外部知識或環境取得資料，再依觀察調整後續步驟。

例：查圖書館今晚是否開館 → 查官方頁 → 讀取時間和公告 → 對照今天日期 → 回答或說明無法確認。

「行動—觀察—更新」是入門示意；論文 benchmark 結果不代表所有產品或任務都會提升。

05 · 控制方式

Workflow 和 Agent 有何不同？

Workflow

路徑預先安排，適合步驟穩定、容易驗收的任務。

A→B→C

Agent

模型會根據任務與工具結果，動態選下一步。

A→工具↘B / C

也可以混合：外層固定流程，內層讓 Agent 彈性處理某一步。

這兩種稱呼在不同框架文件中可能有細微差異；比較時看控制路徑是否固定。

06 · 適用情境

什麼時候值得使用 Agent？

適合探索

任務需要多步查找、工具結果會改變後續路徑。

先用簡單方案

一步即可答完，或固定程式流程更容易驗收。

考量代價

自主性可能帶來較多延遲、成本與錯誤累積。

先用能完成任務的最簡單做法；確認多步決策有實際價值，再增加自主程度。

這是設計指引，實際選擇仍要用自己的任務與限制評估。

07 · 多 Agent

把工作分給多個 Agent？

協調者→研究子任務+整理子任務→整合結果

先寫清楚

每個專家的輸入、輸出和範圍。

安排整合

誰負責收斂結果、交付最終答案？

評估複雜度

分工收益是否大於協調成本？

多 Agent 是選項，不是品質保證。若任務單一且範圍清楚，一個 Agent 或固定 workflow 可能更合適。

Multi-agent orchestration 對應供應商 runtime 細節會持續更新；本頁只教分工概念。

08 · 可靠性

Agent 需要護欄和停手點

✓

定義任務完成條件，不能只靠 Agent 自稱完成。

✓

檢查工具輸出能否支持最後答案。

✓

設定最大輪數、時間/成本與人類確認點。

✓

不確定或工具失敗時，回報限制並停止。

工具回傳是可觀察的環境訊號，但仍要驗證它是否相關、正確、足以完成任務。

Agent 的長處是能推進多步工作；它也可能延長錯誤鏈，所以需要監測和停止條件。

09 · 來源與回顧

記住這三件事

Agent 不只是模型

它還需要工具、上下文和控制流程。

Agent 不一定更好

固定步驟容易驗收時，Workflow 可能更合適。

行動結果要檢查

定義停止條件，必要時讓人確認。
